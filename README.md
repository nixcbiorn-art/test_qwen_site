# Парсер и монитор

## Установка
```
pip install -r requirements.txt
playwright install
```

## Настройка
Через UI (рекомендуется): вкладка "Настройки" в WPF-приложении (ParserApp) —
там выбор скрипта (Monitor/Crawler), Site URL, API Base URL, логин/пароль,
интервал проверки, headless-режим, и редактируемый список API-эндпоинтов.
Для каждого endpoint'а отдельно выбирается **способ взаимодействия**
(колонка "Способ доступа"):

- **none** — без авторизации вообще. Для открытых/публичных API, которым
  не нужен ни токен, ни логин. Запрос уходит без заголовка `Authorization`.
- **token** — свой статический токен именно для этого endpoint'а (колонка
  "Token"). Логин через браузер для него не выполняется.
- **login** — общий токен, полученный логином по Username/Password (через
  `auth.get_auth_token()`, Playwright-браузер). Полезно, когда токен нужно
  получать заново при каждом запуске и сайт не даёт долгоживущий API-ключ.

Кнопка "Сохранить настройки" пишет `data/settings.json`, который
`config.py` подхватывает автоматически при следующем запуске Python-скрипта.

Вручную (если не используешь GUI):
1. `config.py` — дефолтные URL, логин, пароль, список `API_ENDPOINTS`
2. `auth.py` — селекторы формы авторизации (если логин через браузер)
3. `data/settings.json` — можно редактировать напрямую, формат:
```json
{
  "site_url": "https://example.com",
  "api_base_url": "https://api.example.com/v1",
  "username": "",
  "password": "",
  "check_interval_seconds": 300,
  "headless_browser": true,
  "selected_script": "monitor",
  "endpoints": [
    {"path": "/data/public-feed", "auth_mode": "none"},
    {"path": "/data/status", "auth_mode": "token", "token": "my-static-token"},
    {"path": "/data/items", "auth_mode": "login"}
  ]
}
```
`auth_mode` определяет, как парсер обращается к конкретному endpoint'у:
- `"none"` — без авторизации, для открытых/публичных источников;
- `"token"` — используется свой статический `token` этого эндпоинта, логин
  через браузер не выполняется;
- `"login"` — используется общий токен, полученный через
  `auth.get_auth_token()` (Username/Password).

Если `auth_mode` не указан (старый файл настроек) — режим определяется
автоматически: непустой `token` → `"token"`, иначе → `"login"`.

### Пагинация — обход ВСЕХ страниц источника

По умолчанию парсер делает один запрос по URL, указанному в `path` — то
есть, если у источника есть пагинация, вы получите только одну страницу.
Чтобы обойти все страницы и объединить их в один список, добавьте
`"paginate": true`:

```json
{"path": "/estate/x?page[size]=50&page[number]=1", "auth_mode": "token",
 "token": "...", "paginate": true, "max_pages": 100}
```

Тип пагинации определяется автоматически по параметрам, которые уже есть
в `path`:
- `page[number]` или `page` — постраничная (номер страницы растёт на 1);
- `offset` — по смещению (растёт на значение `limit`/`page[size]`).

Если ни один из этих параметров не найден — пагинация не поддерживается
для этого URL, и делается один обычный запрос. `max_pages` (по умолчанию
50) — защита от бесконечного обхода.

### Маппинг — нормализация полей между источниками

Разные API отдают данные в разной структуре (`data`, `results`, вложенные
`attributes.price` и т.п.). Чтобы сравнивать изменения по конкретным
полям (а не по всему сырому JSON), задайте `mapping`:

```json
{"path": "/estate/x", "auth_mode": "token", "token": "...",
 "items_path": "data",
 "mapping": {
   "id": "id",
   "title": "attributes.name",
   "price": "attributes.price.value"
 }}
```

- `items_path` — где в ответе лежит список элементов (`"data"`,
  `"results.items"` и т.п.). Пусто — парсер сам попробует найти список
  среди типичных ключей ответа.
- `mapping` — `{"выходное_поле": "путь.в.json"}` для одного элемента
  списка. Путь через точку, числовой сегмент — индекс в списке
  (`images.0.url`). Пусто — элементы сохраняются как есть, без
  нормализации.

Если каждый нормализованный элемент содержит поле `id`, детектор изменений
(`detector.py`) сравнивает списки по `id` и показывает конкретно: какая
запись добавилась, пропала, и в каком поле у существующей записи
изменилось значение — вместо общего "список изменился".

В ParserApp (UI) это настраивается прямо в таблице эндпоинтов: колонка
"Пагинация" — чекбокс, колонка "Маппинг" — кнопка "Настроить…", которая
открывает диалог для `items_path` и списка полей.

### Превью для LLM — дешёвая и быстрая проверка полей

Если mapping настраивается/проверяется с помощью нейросети (например,
попросить LLM подобрать `mapping` под новый источник или сверить, что
маппинг верный), не нужно скармливать ей весь ответ API — это дорого по
токенам и медленно. Вместо этого:

```bash
python preview_endpoint.py          # список эндпоинтов с номерами
python preview_endpoint.py 0        # превью эндпоинта №0 в консоль
python preview_endpoint.py 0 --rows 50 --out preview.json
```

Инструмент реально запрашивает эндпоинт (с учётом `paginate`/`auth_mode`
из конфига) и вызывает `preview.build_field_preview_json()`, который
готовит компактную выжимку:
- `approx_keys` — свод всех путей полей, встретившихся в выборке
  (`"attributes.price.value"` и т.п.), с одним примером значения на
  каждый — этого достаточно, чтобы понять структуру данных;
- `rows` — первые N элементов (по умолчанию 100) как есть.

Итоговый объём почти не растёт вместе с размером реального датасета
(датасет из 100 и из 10 000 записей дают превью примерно одного размера)
— именно поэтому это в разы дешевле для LLM, чем передавать весь ответ.
Получившийся JSON можно вставить прямо в промпт с просьбой предложить или
проверить `items_path`/`mapping` для этого эндпоинта.

### Импорт готового маппинга от нейросети

Когда LLM вернула готовый mapping, применить его можно двумя способами —
без ручного редактирования JSON:

**В ParserApp:** открой диалог "Маппинг" для нужного endpoint'а (кнопка
"Настроить…" в таблице эндпоинтов), вставь JSON-ответ LLM в поле "Импорт
готового маппинга от нейросети" и нажми "Импортировать" — таблица полей
заполнится автоматически. Останется нажать "Сохранить" в диалоге, а затем
"Сохранить настройки" в главном окне.

**Через CLI (без запуска UI):**
```bash
python apply_mapping.py                        # список эндпоинтов с номерами
python apply_mapping.py 0 llm_mapping.json      # применить к эндпоинту №0
python apply_mapping.py 0 llm_mapping.json --paginate  # заодно включить пагинацию
```

Ожидаемый формат `llm_mapping.json` (именно так стоит просить LLM вернуть
ответ):
```json
{
  "items_path": "data",
  "mapping": {"id": "id", "title": "attributes.name", "price": "attributes.price.value"}
}
```
Также принимается файл, где верхний уровень — сразу словарь маппинга, без
`items_path`. Инструмент точечно обновляет только `items_path`/`mapping`
(и, если указан флаг, `paginate`) у выбранного эндпоинта в `settings.json`
— остальные настройки (токен, auth_mode и т.п.) не трогает.

**Важно про безопасность:** пароль и токены хранятся в `settings.json` в
открытом виде (без шифрования). Это локальный dev-инструмент, не размещай
файл в публичных репозиториях и не давай доступ к `C:\parser\data\` другим
пользователям машины.

## Скрипты (папка scripts/)
- `scripts/setup-python.bat` — ставит pip-зависимости и браузеры Playwright (двойной клик или запуск из cmd)
- `scripts/install-dotnet-sdk.ps1` — проверяет, есть ли .NET 8 SDK, и ставит его, если нет
- `scripts/run-parser-app.ps1` — restore + build + run для ParserApp (WPF)

Все .ps1/.bat файлы написаны на английском (ASCII) намеренно — PowerShell 5.1
на Windows без BOM в файле читает кириллицу в системной кодировке, а не
UTF-8, из-за чего скрипт может не распарситься. Так надёжнее.

Запуск PowerShell-скриптов (из PowerShell, не из cmd):
```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force
cd C:\parser\scripts
.\install-dotnet-sdk.ps1
.\run-parser-app.ps1
```

## Структура
- `config.py` — настройки
- `auth.py` — авторизация через Playwright, получение токена
- `api_client.py` — HTTP клиент для API
- `scraper.py` — парсинг отдельной HTML-страницы через Playwright
- `crawler.py` — грубый обход всего сайта (BFS по внутренним ссылкам)
- `storage.py` — работа с SQLite (снимки данных)
- `detector.py` — сравнение снимков и определение изменений
- `monitor.py` — основной цикл мониторинга
- `main.py` — точка входа

## Полный обход сайта (crawler.py)
```
python crawler.py
```
Обходит сайт из `SITE_URL` по внутренним ссылкам (BFS), сохраняет HTML каждой
страницы в `data/pages/` и пишет метаданные (url, title, статус, хэш контента)
в таблицу `pages` в той же SQLite-базе.

Настройки в `config.py`:
- `CRAWL_MAX_PAGES` — лимит страниц за один запуск (защита от бесконечного обхода)
- `CRAWL_DELAY_SECONDS` — пауза между запросами
- `CRAWL_OUTPUT_DIR` — куда складывать HTML-файлы
- `CRAWL_INCLUDE_QUERY` — учитывать ли `?query`-параметры как отдельные страницы

**Ограничения этой версии:**
- не проверяет `robots.txt` и не подстраивается под `Crawl-delay` сайта
- не отличает контентные дубли (пагинация, сортировки, utm-метки)
- не резюмирует прерванный обход — повторный запуск начинает с нуля
- не рендерит контент, который подгружается позже `networkidle` (бесконечный скролл и т.п.)
